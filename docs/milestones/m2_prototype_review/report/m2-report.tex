\begin{abstract}
Milestone 2 asks for an initial deployment, a CI/CD pipeline, and basic
functionality. Lecture Indexer (LI) meets all three. Terraform provisions
the production environment on Google Cloud and Microsoft Azure. A GitHub
Actions pipeline tests every push and releases every merge to
\texttt{main} after one human approval, with automatic rollback. It has
shipped three tagged releases. In production, a professor signs in with
Google and registers a YouTube lecture, LI indexes its auto-generated
captions, and a student searches the course and jumps to the moment a word
is spoken. This report maps each deliverable to the evidence in our
repository and explains where the build differs from the Milestone~1
proposal, and why.
\end{abstract}

\begin{IEEEkeywords}
cloud-native, multi-cloud, Kubernetes, CI/CD, Terraform, GitHub Actions.
\end{IEEEkeywords}

\section{Introduction}
Our Milestone~1 proposal described LI, a service that retrieves the timed
captions of recorded lectures from the YouTube Data API, indexes them with
PostgreSQL full-text search, and returns deep links such as
\texttt{?t=202} to the moment a term is spoken~\cite{m1}. Table~\ref{tab:summary}
summarizes how we met each Milestone~2 deliverable. Sections~\ref{sec:deploy}--\ref{sec:func}
give the evidence for each one. All source code, workflow runs, and releases
are public at \url{\repo}.

\section{As-Built Architecture}
\label{sec:arch}
Fig.~\ref{fig:arch} shows the system we deployed. The React SPA is
served by nginx on Cloud Run. It calls two Flask services, the Ingest API and
the Search API, on a GKE Autopilot cluster. A global HTTPS load balancer
with a Google-managed certificate routes \texttt{/ingest/*} and
\texttt{/search/*} to them. Each service has its own Horizontal Pod
Autoscaler (1--4 replicas at 70\% CPU) and a Cloud SQL Auth Proxy sidecar
that connects to a private-IP Cloud SQL for PostgreSQL instance using IAM
database authentication. Images are stored in Artifact Registry, and the
database admin password in Secret Manager. Pods reach Google APIs through
Workload Identity, so no service-account keys exist.

\subsection{Changes from the proposal}
\begin{itemize}
\item \textbf{Frontend on Cloud Run, not Azure Static Web Apps.} Our Azure
for Students subscription allows only five regions, and Static Web Apps is
offered in none of them. The frontend therefore runs as an nginx container
on Cloud Run, which scales to zero~\cite{adr1}.
\item \textbf{Azure region.} Azure refused \texttt{eastus2}
(\texttt{RequestDisallowedByAzure}), so all Azure resources are in
\texttt{northcentralus}.
\item \textbf{Invite-only sign-in.} We started with a \texttt{PROFESSOR\_EMAILS}
allowlist. It published email addresses in a public repository and required
a release for every role change. Roles now live in the database: admins
invite users and set their roles on an Admin page~\cite{adr2}.
\end{itemize}

The multi-cloud requirement still holds. Azure hosts the CI deploy
identities, which are federated with GitHub over OIDC, and the production
resource group for the off-site backups (Section~\ref{sec:next}).

\section{Deliverable 1: Initial Deployment}
\label{sec:deploy}

\subsection{Infrastructure as code}
All infrastructure is Terraform, in two stages~\cite{runbook}:
\begin{enumerate}
\item \textbf{\texttt{bootstrap/}} creates the CI identities: a GCP Workload
Identity pool and the service accounts \texttt{github-terraform},
\texttt{github-deploy}, and \texttt{github-plan}, plus the Azure managed
identities \texttt{id-li-github} and \texttt{id-li-github-plan}. Each has
federated credentials scoped to our repository and its \texttt{prod}
environment. State lives in a versioned GCS bucket with public access blocked.
\item \textbf{\texttt{envs/prod}} composes reusable modules
(\texttt{gcp-network}, \texttt{gke}, \texttt{cloudsql},
\texttt{artifact-registry}, \texttt{secrets}, \texttt{cloud-run-frontend})
into 52 resources. We applied it on 2026-10-18; GKE took 7\,min 38\,s and
Cloud SQL 13\,min 4\,s. A fresh plan shows no changes.
\end{enumerate}
CI runs \texttt{terraform validate} and a mocked \texttt{terraform test}
suite (3 tests) on every push.

Kubernetes manifests are Kustomize bases with a \texttt{prod} overlay
(\texttt{deploy/k8s/}). They define Deployments, Services, HPAs, a default-deny
NetworkPolicy, the Ingress with a ManagedCertificate, and a migration Job
that runs numbered SQL migrations before each rollout. \texttt{make
k8s-check} validates the rendered overlays against Kubernetes schemas.

\textbf{Cost control.} \texttt{make cloud-pause} scales the API pods to
zero, deletes the load balancer, and stops Cloud SQL. It keeps all data and
the API hostname, and \texttt{make cloud-resume} reverses it. Idle cost drops
from about \$40--60 to about \$9 per month. Terraform ignores Cloud SQL's
activation state, so an apply never restarts a paused database.

\subsection{Problems found and fixed}
Bringing the environment up exposed three problems. We fixed each one in
code, so that a fresh deployment works the first time:
\begin{enumerate}
\item The Azure region policy (above).
\item The Artifact Registry module did not wait for its API to be enabled.
We added a \texttt{depends\_on}.
\item The repository uses GitHub's immutable OIDC subject format
(\texttt{repo:Owner@id/name@id:\dots}), so no CI binding matched. We added a
\texttt{github\_subject\_prefix} variable to bootstrap.
\end{enumerate}

\section{Deliverable 2: CI/CD Pipeline}
\label{sec:cicd}
The pipeline consists of four GitHub Actions workflows~\cite{release}. None
of them stores a cloud credential. Every cloud action signs in through OIDC
federation to the GCP or Azure identities created by bootstrap.

\subsection{Continuous integration (\texttt{ci.yml})}
CI runs on every push to \texttt{main} and \texttt{development} and on every
pull request. It has six jobs:
\begin{itemize}
\item \textbf{Python:} Ruff lint and format checks, and pytest against a
PostgreSQL~16 service container (93 tests).
\item \textbf{Docker images:} builds the images and runs a smoke test
against the full docker-compose stack.
\item \textbf{Terraform:} format, validate, and the mocked tests, with no
credentials.
\item \textbf{Kubernetes manifests:} kustomize and kubeconform, plus a
namespace check.
\item \textbf{Frontend:} ESLint, Vitest (30 tests), and a production build.
\item \textbf{Frontend image:} builds the nginx image and checks the
security headers it serves.
\end{itemize}
The latest run on \texttt{main} took 40\,s and passed (Fig.~\ref{fig:ci}).

\subsection{Continuous delivery (\texttt{release.yml})}
Every push to \texttt{main} starts one Release run, shown in
Fig.~\ref{fig:release}:
\begin{enumerate}
\item \textbf{ci} waits for CI to pass on the commit.
\item \textbf{review} prints a review sheet of every commit and migration
since the last \texttt{prod-*} tag.
\item \textbf{plan} runs the real Terraform plan with a read-only identity.
\item \textbf{One approval} in the \texttt{prod} GitHub environment
(three team reviewers; deploys only from \texttt{main}).
\item \textbf{release} applies exactly the reviewed plan. Then it backs up
Cloud SQL if there are new migrations, builds and pushes the three images
tagged with the commit SHA, runs migrations, rolls out ingest and search
(undone automatically on failure), and deploys the frontend to Cloud Run
with no traffic. Traffic moves to the new revision only after a health
check passes. A final check calls the API through the load balancer.
\item \textbf{tag} creates \texttt{prod-YYYY-MM-DD.N} and a GitHub Release
listing the commits.
\end{enumerate}
\texttt{rollback.yml} redeploys any earlier tag. \texttt{terraform.yml}
posts a preview plan on pull requests. When the environment is paused, a
release stops before asking for approval.

\subsection{Evidence that it works}
The first production release needed five runs. Table~\ref{tab:runs} shows
that each failure stopped safely, before it changed anything it should not
have. A failed frontend check left the previous revision serving traffic.
After that, the pipeline released \texttt{prod-2026-10-19.1} (invite-only
sign-in, the Admin page) and \texttt{prod-2026-10-27.1} (the embedded
player). Both took one approval and about six minutes.

\section{Deliverable 3: Basic Functionality}
\label{sec:func}
The prototype implements the workflow from the proposal, end to end:
\begin{enumerate}
\item A user signs in with Google (Fig.~\ref{fig:signin}). The APIs verify
the ID token's signature and audience, then look up the user's role. Only
invited users can sign in.
\item A professor creates a course and registers a YouTube video
(Fig.~\ref{fig:manage}). The Ingest API checks that the video belongs to the
professor's own channel and downloads the auto-generated caption track. It
removes word-timing tags, rolling repeats, and sound tags such as
\texttt{[Music]}, merges cues into segments of up to about 20\,s, and stores
them.
\item A student searches the course. The Search API ranks the matches with
PostgreSQL full-text search and returns highlighted excerpts. Each result
plays in an embedded YouTube player at its timestamp (Fig.~\ref{fig:search}).
\item An admin invites users and sets their roles (Fig.~\ref{fig:admin}).
\end{enumerate}

\subsection{Automated tests}
The latest CI run passed 93 Python tests and 30 frontend tests. The Python
tests cover caption parsing against a real VTT fixture, the YouTube client,
routes, invitations, migrations, and query building. The frontend tests
cover the API client, the pages, and the player. With the 3 Terraform tests,
the suite has 126 tests.

\subsection{Observations}
Registering one lecture costs 252 YouTube API quota units, so the default
quota of 10,000 units allows about 39 registrations a day. Searches use no
quota. Because segments are up to 20\,s long, a link opens on average about
10\,s before the word is spoken. Shorter segments would make links more
precise, at the cost of splitting phrases across segments.

\section{Security Already in Place}
The full security review is due in Milestone~3. The prototype already has:
\begin{itemize}
\item Keyless CI and keyless workloads, through OIDC federation and Workload
Identity.
\item The database admin password in Secret Manager.
\item IAM database users with least-privilege group roles: read-write for
ingest; read-only for search, except claiming invitations on the
\texttt{users} table.
\item Cloud SQL reachable only on a private IP, and a default-deny
NetworkPolicy.
\item A Content Security Policy that allows connections only to the API and
Google Sign-In.
\item Invite-only sign-in with role-checked endpoints.
\end{itemize}

\section{Next Steps (Milestone 3)}
\label{sec:next}
For Milestone~3, we plan to add:
\begin{itemize}
\item A nightly backup CronJob that writes an encrypted \texttt{pg\_dump}
to immutable, cool-tier Azure Blob Storage.
\item A Cloud Monitoring dashboard and alerts, built on the structured logs
the services already emit (\texttt{http\_request},
\texttt{youtube\_api\_call}).
\item A written security review.
\item Developer onboarding documentation.
\end{itemize}
